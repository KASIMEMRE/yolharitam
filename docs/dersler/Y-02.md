# Y-02 · Görünen ad — Ders notu

## Bu PR'da ne değişti?
Profil sekmesine "Görünen ad" alanı ve Kaydet butonu eklendi; Yol Haritam başlığında artık "Merhaba, <ad>" yazıyor. Adı okuyup kaydeden iş, ortak bir **hook**'a (`useDisplayName`, React'te durum + mantığı paketleyen `use...` fonksiyonu) taşındı; iki ekran da onu kullanıyor. Veri Supabase'deki `profiles.display_name` sütununda duruyor. Kaydederken **RLS** (Row Level Security: veritabanının "bu satıra kim dokunabilir" kuralı) sessizce engel olabilir; bunu da koduyla yakalıyoruz.

## Kavramlar

### 1. Türetilmiş state: efektle eşleme, render'da hesapla
- Ne: Market fişinde "toplam" satırını ayrıca yazıp güncellemezsin; kalemlerden her seferinde hesaplarsın. Hesaplanabilen değeri ayrı state'te tutarsan iki kopya birbirinden kopar.
- Bizim kodda: `src/app/(tabs)/profile.tsx:37` ve `:43-47`
  ```tsx
  const [draft, setDraft] = useState<string | null>(null);
  ...
  const value = draft ?? name ?? '';
  const trimmed = value.trim();
  const changed = trimmed !== (name ?? '');
  const saveDisabled = nameStatus !== 'ready' || saving || !changed;
  ```
  `draft` kullanıcının yazdığıdır (`null` = henüz yazmadı). Alan, yazı varsa onu, yoksa sunucudaki adı, o da yoksa boş metni gösterir. `changed` ve `saveDisabled` de ayrı state değil, her render'da yeniden hesaplanır. Kayıt başarılı olunca `setDraft(null)` (`:67`) alanı tekrar kayıtlı ada bağlar.
- Yaygın hata: "Sunucudan ad gelince `useEffect` ile `setValue(name)` yapayım." Bu, kullanıcı yazarken gelen geç cevabın yazdığını ezmesine ve fazladan render'a yol açar.

### 2. Yarış durumu (race condition): `cancelled`, `writeVersion`, `stale()`
- Ne: İki kişi aynı anda tahtadaki skoru güncellemeye çalışsın; en son silgiyi kim vurursa o kalır, doğru olan değil. Ağ istekleri de böyle: yavaş gelen eski cevap, yeni cevabı ezebilir.
- Bizim kodda: `src/hooks/use-display-name.ts:34-37` ve `:49-52`
  ```ts
  let cancelled = false;
  const versionAtStart = writeVersion.current;
  const stale = () => cancelled || saving.current || writeVersion.current !== versionAtStart;
  ...
  } catch {
    if (!stale()) setState((s) => ({ ...s, status: 'error' }));
  }
  ```
  Okuma başlarken sayaç not edilir. Cevap dönünce ekran ayrıldıysa, kayıt sürüyorsa ya da arada kayıt olup sayaç değiştiyse cevap atılır. `save` başında ve sonunda sayacı artırır (`:65`, `:85`). Efektin temizleme fonksiyonu (`:55-57`) `cancelled`'ı `true` yapar. `useFocusEffect` (`:29`) ile her odakta ad yeniden okunur; böylece Profil'de değişen ad Yol Haritam'a geçince güncel görünür.
  Ders: incelemede `catch` dalında bu korumanın unutulduğu yakalandı. Başarı yolunu korumak yetmez; hata yolu da aynı `stale()` süzgecinden geçmeli, yoksa eski bir hata yeni sağlıklı durumu "error"a çevirir.
- Yaygın hata: `ref` yerine `useState` kullanmak. State güncellemesi sonraki render'da görünür; async fonksiyonun içindeki eski değeri görmesi (closure) yüzünden kontrol yanlış çalışır. Ref ise anında okunur ve render tetiklemez.

### 3. RLS sessiz başarısızlığı ve doğrulamanın yeri
- Ne: Kapıcı yanlış katı "giremezsin" demek yerine sessizce seni içeri almamış olabilir. Postgres'te RLS yüzünden `update` hata vermeden **0 satır** etkileyebilir; uygulama "kaydettim" sanır.
- Bizim kodda: `src/hooks/use-display-name.ts:69-78`
  ```ts
  const { data, error } = await supabase
    .from('profiles')
    .update({ display_name: trimmed })
    .eq('id', uid)
    .select('display_name')
    .maybeSingle();
  if (error) { ... }
  if (!data) return { ok: false, message: ERROR_TEXT.profileSaveFailed };
  ```
  `.select()` güncellenen satırı geri ister; `.maybeSingle()` satır yoksa hata yerine `null` verir. `data` boşsa kayıt gerçekleşmemiştir. Ekran tarafında `trim` ve `maxLength` (40) vardır (`profile.tsx:25`, `:116`), ama bu yalnız **istemci doğrulaması**: kullanıcıyı yönlendirir, güvenlik sağlamaz. Sunucu tarafı `CHECK` kısıtı bu PR'da yapılmadı (bilinen eksik); API'yi doğrudan çağıran biri 40 karakteri aşabilir.
- Yaygın hata: Yalnız `error` var mı diye bakıp "hata yok = başarılı" saymak.

## Kendin dene (10-15 dk)
`src/hooks/use-display-name.ts:78` satırındaki `if (!data) return ...` satırını geçici olarak yorum satırı yap. Sonra `save` içindeki `.eq('id', uid)` kısmını `.eq('id', '00000000-0000-0000-0000-000000000000')` yap (olmayan bir satır). Telefonda Profil'de adı değiştirip Kaydet'e bas. Hangi mesajı görüyorsun? Ardından iki satırı eski haline getir ve aynısını tekrarla; bu sefer ne değişti?
Ardından düşün: Neden ilk denemede hata yok, ama ad da kaydedilmiyor?

<details>
<summary>Cevap</summary>

Sorgu hata dönmez, çünkü "0 satırı güncellemek" Postgres için geçerli bir işlemdir. Korumayı kapatınca kod `data` içinde ad arar, `null` bulur ve `data.display_name` bir istisna fırlatır; `catch` bunu yakalayıp yanıltıcı bir "bağlantı" mesajı gösterir. Yani gerçek sorun (satır güncellenmedi) yanlış teşhis edilir. Koruma geri gelince `data` boşsa net biçimde "kaydedilemedi" denir. RLS engeli de aynı şekilde sessiz davranır; bu yüzden `.select().maybeSingle()` ile "satır döndü mü" diye bakıyoruz.
